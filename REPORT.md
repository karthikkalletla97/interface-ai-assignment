# Design write-up

This is a system that lets an LLM figure out how to do a task in a UI that has no API, saves that run as a reusable capability, and then replays it later without the model. I built it against a fake bank app I wrote (a "mock bank") that's made on purpose to look like old, messy internal software.

## 1. Architecture

There are three parts, and they pass work to each other through files instead of being one big program. Discovery is the LLM part: it looks at the page, picks one action, does it, and repeats until the goal is done or it hits a stop condition (goal reached, too many steps, timeout, or a dead end). Distillation takes that successful run and turns it into a clean capability file. Replay runs that file with no model involved. Each part is its own command, and the saved artifact is the handoff between them.

I built it in NestJS standalone mode, so I get dependency injection and clean modules but no web server, and I run it from the command line. The stack is TypeScript, Playwright to drive the browser, the Anthropic SDK for the one model call per step during discovery, and Zod for the artifact schema. Artifacts are just versioned JSON on disk. There's no database, no queue, and no cluster, because the loop doesn't need any of that and the brief says it doesn't want infrastructure built before it's needed. The spots where it would grow later (a surface adapter, the policy file, an artifact store) are left as clean boundaries instead.

Two choices matter most. First, the model is only used in discovery. Replay has no model on purpose, because the whole point of the artifact is to be the cheap, repeatable, trustworthy part, and a model step in the middle of that would be unpredictable. Second, I never send the model raw HTML. Each step I send it only the clickable things (their role, their label, and what's typed in them) plus a short chunk of the page text. That's my answer to the requirement that it should still work on a page with no clean HTML, and it keeps each model call small and accurate as pages get bigger. I didn't reach for a framework like LangGraph because only discovery uses the model and it's a simple loop. I'd use one if discovery ever needed branching plans or the ability to save and resume a run partway through.

## 2. Artifact schema

I build the artifact from a real run, not by asking the model to summarize it. Every step in it actually happened, because it comes straight from the recorded run. During distillation I drop the pointless steps the model took (like navigating to a page it was already on), tie each typed value to a named input, build a locator for each step, and work out the outputs and the success check from where the value actually showed up on the last page.

The file holds a versioned capability (id, name, description, version), typed inputs (name, type, required, secret), the ordered steps, typed outputs with a rule for reading them, a success check, and where it came from. Each step says how to find its target: first by role and label, then a backup chain of visible text and finally position, plus a short note on why that's stable. Inputs bind by field name first and by the typed value second. That's what lets me hide a password in the log but still bind it correctly. It's also why no secret ends up in the artifact: the step just points at the "username" input by name, it never stores the actual password, and secret inputs don't keep an example value. Outputs get read by their label, the number next to "Savings," which I work out by finding the value in the page text, so it still works if the table layout changes. Each step also has a risk tag. Zod checks the file when I write it and again when replay loads it, so a broken capability never runs. The "where it came from" field points at the run id, not the raw model log, so you can trace it without the artifact being the log.

## 3. Determinism & error handling

Replay is repeatable because nothing makes a decision while it runs. Locators try a fixed backup chain, waits are explicit (wait for the network to go quiet, and after typing, read the field back to make sure the value stuck before moving on), and the success check runs before any output comes back. The same file and the same inputs give the same steps and the same result every time.

When something happens at runtime, I sort it into one result type that I always return and never throw, so a normal outcome and a real failure can't share the same path. The brief says mixing those two up is the most common mistake, so I made it structural. The types are: a business outcome (a known page like "no member found," "restricted," or a form error, which is a real answer the caller wants, not a crash); a recoverable one, which isn't a final state but something I handle mid run (dismiss a known notice, or wait and retry a slow load with backoff) and then land on one of the final states; a hard failure (an element that won't resolve after retries, or a failed success check) that reports the step, what I expected, and what I saw; and an escalated state for a risky step that needs a person. I match on the full text of a page, not loose keywords, so the search page's own hint (which literally contains the words "restricted," "notice," and "not found") doesn't set off a false outcome. I unit tested that. UI drift gets handled by the same backup locators and the label based read.

## 4. Heterogeneity & multi-tenant

I only built the web version, but the design isn't stuck there. The key idea is a surface adapter that turns any surface into the same simple view (role, name, value, text) and runs the same small set of actions (navigate, type, click, select). The recorded flow only talks in roles and labels, and those exist not just in a browser but in the accessibility tree that browsers and desktop apps both have. A normal web app uses the Playwright adapter. A legacy web app of tables with no ids is already covered, my member page is exactly that kind of page, and framesets would just need the adapter to look inside each frame, which is a small change. A desktop app would swap in an OS automation driver (like UI Automation on Windows) that gives the same role and label tree. The artifact and the replay engine don't change at all. Only the adapter that reads and acts on the surface changes. That's the split between how you act on a surface and the flow you recorded.

Reusing a capability across many banks works because the artifact is already parameterized: real values are inputs, not hardcoded, so a capability recorded on the vendor's app isn't tied to one bank. I'd do the same with URLs, turning /member?id=100001 into a pattern over the memberId input. Then one base artifact covers every bank running that vendor's app, and the differences between banks (a renamed field, an extra step, different branding) are small override files layered on top, so I store one base plus a few small patches instead of recording the whole flow again for each bank. I can spot drift with what I already have: if a base locator stops matching for one bank, or a success check fails, that's the signal. I flag that one step for a look, or a limited, policy checked model fix of just that step, instead of throwing the whole capability away. Version numbers on the artifact and a per bank success rate make drift show up early and let me hold back unattended replay until a capability looks healthy.

## 5. Escalation & handoff

I detect "stuck" from real signals, not a guess. Replay returns escalated for a risky step, a hard failure when it can't recover, and a session expired signal, and discovery returns a give up and a "same action three times" stuck signal. Any of those can pull in a human.

In handoff mode, replay opens a real visible browser and, at the risky step, doesn't do it. It hands control over (a flag flips from agent to human), prints an intervention request with what the person needs (which capability, which step, why, the current url, and a screenshot), and leaves the same live browser open, the one it was already using, not a new one. The person does the step in that window and presses Enter. Replay then records what changed (the page before and after, and whether it changed), takes control back, and finishes the success check. It ends as a success with the handoff written into the result and the evidence. The control model is one flag that always says who's driving, and I log every switch. Pause means stop before the action and hand over. Resume means record and take control back. Same browser the whole time. The operator screen is just a command line prompt, which the brief says I can fake, but the pause, hand over, record, and resume part is real. The same code would work for a stuck discovery run too; I wired the live demo into replay and left the discovery side as a clean hook.

## 6. Safety

The guard has two layers. The allowlist is the outer wall: which origins, which routes, and which action types are allowed, checked before every action in both discovery and replay, and anything outside it is blocked. Inside that, risk classification is the inner gate: each step gets a risk tag when I distill it, so a click on a button whose name means "commit" (confirm, delete, transfer) is risky, and replay knows without working it out again. Risk lives in the artifact because it's part of the step. The allowlist lives in a config file because it's a runtime setting. A risky step never just goes ahead: with no one watching it returns escalated, and with a person there it goes through the live handoff. There's also an approval flag as a stand in for a person saying yes.

Secrets get handled two ways. The artifact points at inputs by name, so a password is never written into the capability at all. And in the logs, I mask declared secret values plus known PII patterns (the SSNs and emails on the member record) so nothing sensitive sits in the evidence. The allowlist and the input list are also the real answer to a bug I found while testing: with a vague goal, the agent once grabbed a member id off a hint on the page. In this kind of system the caller decides which record to touch and the agent only does it, so the allowed scope and the input list enforce that instead of trusting the prompt.

The limits are worth being honest about. The allowlist matches by route prefix, so it's coarse: it can say "you may act on /member" but not "you may read a balance but not open a sub account." The risk tag is worked out from the button's name and the route it hits, so a commit that has neither an obvious name nor an obvious commit route could get tagged safe by mistake. The approval flag is a stand in, not real identity or sign off. And redaction only masks the values I declare as secret plus the PII patterns I already know about, so a new sensitive field would need to be added to the list.

## 7. Cuts

The cuts are on purpose and written down where they happen. The operator screen is a command line prompt, not a shared browser the operator watches; the mechanism is real and the screen is the fake part. Desktop and cross bank support are designed above but not built, since the brief asks for one real surface. The page text I send the model is just the first chunk, capped, so a value far down a very long page could be missed; the fix is to grab the relevant section instead of a blind chunk, and the list of clickable things stays small anyway. The account type in the sub account flow stays on its default instead of being an input, to keep the demo on the risky confirm; making it an input would add a select step. The allowlist runs in both loops, but the live handoff demo is only wired into replay. A limited model fix for a single failed step, and a confidence score that decides when replay can run unattended, are described above but not built.

If I had more time, in order: the surface adapter with a second adapter (a frameset or desktop app) to prove the split works; per bank override files plus a drift signal from success rates; and the single step model fix behind the existing guard. After that the operator screen becomes a small real console, and discovery gets the same handoff replay already has.

One testing note: you can't reliably pass an empty string through npm and PowerShell, so I trigger the form validation case with a space, which the server trims to empty.
